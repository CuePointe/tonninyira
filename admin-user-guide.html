TONNINYIRA ADMIN GUIDE

Checking admin access…

Run the marketplace with discipline.

This is the administrator’s operating guide for Tonninyira: customer activity, vendors, riders, orders, payments, support, approvals, analytics and system health. Use it as the daily runbook—not just as documentation.

Golden rule: browsing can be public, but transactions and sensitive operations must be authenticated. Never place service-role keys or payment secrets in frontend files.

1. Start the system

1
Open the marketplace and verify the public browsing experience loads without signing in.
2
Sign in with the approved admin account. Open Account → Admin Control Tower.
3
Press Refresh in the control tower before making decisions. Treat the dashboard as the current operational snapshot.

2. Understand the control tower

The control tower is organized around nine decision areas:

Overview = health & economics · Operations = live orders · Customers = demand & retention · Vendors & riders = supply · Payments & payouts = money · Support = service · Approvals & trust = onboarding & reputation · Growth & analytics = behaviour · System data = data inventory.

3. Daily operating routine

A
Open with Overview. Check GMV, platform fees, order count, completed orders, customer count and event volume.
B
Check Operations. Look for pending/failed payments, stuck fulfilment statuses, unusual cancellations and orders without a rider.
C
Check Partners. Review pending vendor/rider approvals, partner readiness and payout requests.
D
Reconcile money. Compare payment transaction status with platform settlement records before confirming any payout or manual adjustment.
E
Clear support. Work the oldest unresolved conversations first; record the resolution in the normal support workflow.
F
Read demand signals. Check order geography, repeat users, reviews and wishlist activity. Move supply toward evidence, not guesses.

4. Customer management

Use the Customers view to identify:

• customers with orders but no repeat activity;
• high-intent users saving many items;
• customers who have stopped ordering;
• loyalty engagement and review behaviour.

Strategy: a wishlist save is a demand signal. Many saves with few orders can indicate price friction, weak delivery coverage, poor trust or checkout friction.

5. Vendor & rider management

Use the partner view to monitor approval status, location, category, ratings, readiness and payout requests. Approve only after the required onboarding evidence has been checked through the proper workflow.

Strategy: measure supply productivity, not just partner count. A smaller set of active, reliable vendors can outperform a large inactive network.

6. Order operations

For every problematic order, establish the sequence:

customer → order created → payment initiated → payment verified → vendor prepares → rider assigned → fulfilment completed → settlement recorded

When an order looks wrong, find the first broken state in that chain. Do not “fix” the last visible symptom while leaving the earlier state inconsistent.

7. Payments & payouts

Review payment_transactions for provider, amount, status, TX reference, network and verification time. Review platform_settlements for gross, platform fee, vendor net and rider net.

Never store Flutterwave secret keys, webhook secret hashes, service-role keys or bank/mobile-money credentials in GitHub frontend code.

8. Support discipline

Use the support inbox to triage by urgency:

Payment issue → verify transaction before promising a refund.
Missing order → inspect order + events.
Vendor complaint → inspect partner status and order history.
Account issue → verify session and profile, never request a password.

9. Approvals, trust & reputation

Use role requests, reviews and partner approval data together. Watch for repeated low ratings, unusual review patterns, unapproved accounts attempting to transact, and supply partners with poor reliability.

10. Growth & market strategy

Use the analytics section as a decision loop:

1
Acquisition: track visits and meaningful marketplace actions.
2
Conversion: compare product/stall views, wishlist saves and completed orders.
3
Retention: monitor repeat ordering users, review activity and loyalty engagement.
4
Geography: identify areas where demand is concentrated and where delivery coverage is weak.
5
Supply: recruit or activate vendors where demand is proven, not merely where supply is easiest to find.
6
Economics: watch GMV, platform fee, vendor earnings, rider economics, payment success and cancellation leakage together.

11. Weekly management review

Record a simple weekly scorecard: total orders, completed-order rate, GMV, platform fees, payment success, repeat-user rate, average order value, active vendors, active riders, support backlog, cancellations and top demand areas.

12. System health

Use System data to confirm tables are returning records where expected. If a table suddenly stops changing, check the corresponding workflow, database policy, frontend script and Edge Function rather than assuming demand disappeared.

13. GitHub deployment workflow

Tonninyira is maintained on the tonninyira-enhancements branch. The repository workflows automatically inject parts of the enhancement layer and integrate the account/session/payment/PWA scripts when their tracked files change. After a code change:

1
Commit to tonninyira-enhancements, not main.
2
Open GitHub Actions and confirm the relevant workflow finishes successfully.
3
Open the site and perform one real smoke test: browse → sign in → account → admin control tower.
4
For payment changes, also test payment initiation and payment-return handling in a controlled environment before calling it production-ready.

14. When something breaks

“Sign in again” → confirm the shared Supabase session is present and use the account UI to sign out/in once.
Admin denied → confirm the signed-in profile has admin/staff authorization in the database.
Data table empty → check RLS, table permissions and whether the feature is actually writing data.
Payment pending → inspect provider reference, payment transaction status and webhook/verification path.

15. Security rules

Do not share admin credentials. Do not ask users for passwords. Do not put privileged Supabase keys in frontend code. Treat customer phone numbers, order history and payment references as operationally sensitive. Use database RLS as the real access boundary; the admin page’s UI check is not a substitute for RLS.
